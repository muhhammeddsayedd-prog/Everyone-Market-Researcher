everyone. Market Radar — Codex skills installation plan
Prepared: 17 October 2026
Status: recommendation and installation brief only. No skills have been installed into the project. No packages, hooks, helper scripts, workflows, deployments or paid providers were executed for this review.
Selection: 29 upstream skill entries (22 Addy + 4 Vercel + 2 Supabase + 1 n8n), plus one proposed local delivery skill. The n8n release payload still needs verification.
Basis and review limits
This selection is grounded in the four supplied repository descriptions (including the two attached text files), live GitHub catalogs and selected manifests, current official Codex/Supabase documentation, and the existing Market Radar handoff/review baseline. Milestone assignments and install/defer/exclude decisions are project-specific recommendations, not upstream requirements. This was not an exhaustive security audit of every repository file or an execution test of the skills.
The project remains Next.js/TypeScript/Vercel + Supabase + n8n Cloud, with the approved provider collectors, OpenAI extraction/evaluation, REST/MCP and email. Existing M00–M15 scope, approval boundaries and testing criteria remain the source of truth. Skills do not replace them.

One proposed local skill: emr-milestone-delivery
This is not an existing skill in the four repositories and has not been created. Its purpose is to route work through the existing project record, not to duplicate it or invent another roadmap.
It should read AGENTS.md, PROGRESS.md, DECISIONS.md, the current milestone, relevant architecture/testing documents and the review findings. It should select technical skills by task; implement the complete approved milestone; record tests actually run, limitations and real external actions; update the existing progress/handoff; preserve completed work; and stop at genuine authorization or milestone boundaries.
Project-specific checks to route into the relevant tests include durable callback intake/completion, safe watermarks and claim fencing, reliable deduplication, retries for discovered-but-uncrawled pages, partial-observation handling, Cloud-compatible validation, source-domain eligibility, design-token parity, cost-unit consistency and unambiguous schedules. A skill cannot itself prove these are fixed.
Keep the Everyone design system authoritative. Keep source text untrusted and provenance reviewable. Preserve public-only collection, approved actors, thumbnail-only storage and latest engagement metrics. Operational telemetry is not permission to add a historical engagement dataset.
Installation rules
Use project-scoped .agents/skills/ for Codex. Inspect existing project and global skills first for duplicates or name collisions; do not delete or replace them automatically. Do not install the same source through both a plugin and copied folders without resolving duplicate discovery.
Resolve an immutable source commit or release before each import, preserve upstream licenses, record source paths and file hashes, and record reviewed local patches separately. The main URLs in the allowlist are discovery references, not version locks. Pin the installer itself when it is used.
Copy complete selected directories and all required resources. Preserve or deliberately repair relative references and test them. Do not import upstream root AGENTS.md, CLAUDE.md, hooks, MCP credentials or broad settings automatically. Prefer copied folders on installations where symlink behavior has not been verified.
Review helper scripts and external destinations before execution. Do not print tokens, scrape arbitrary credential files, run opaque remote scripts, broaden tool permissions, change paid plans, activate schedules or deploy just because a skill suggests it. Updating skills is a reviewed dependency update, not an automatic step before every session.
For selected skills requiring explicit invocation, merge the following into agents/openai.yaml, preserving existing metadata and dependencies:
policy:
  allow_implicit_invocation: false
Apply explicit-only policy at least to spec-driven-development, constraint-driven-development and vercel-optimize. This affects skill selection, not authorization: it does not make a paid run, production write or secret access safe by itself.
Skills versus actual capabilities
A skill provides procedure; it does not establish authenticated access or install a browser/test runner. Codex still needs the intended repository access, Supabase tooling and correctly scoped environments, n8n tools matching the actual connected server, a verified Vercel target, and the project’s Vitest/Playwright/axe/pgTAP tooling. DevTools-specific inspection requires the relevant browser integration.
The four catalogs do not supply a dedicated audited skill for every approved Apify actor, OpenAI extraction/evaluation contract, Firecrawl/SerpAPI integration, Resend setup or production MCP server implementation. Use the existing provider specifications and current official documentation. Missing specialized skill names are not permission to fabricate actor inputs or substitute another architecture.

Do not begin or advance application development as a side effect.

Verification checklist
Acceptance of setup requires valid frontmatter; expected unique skill names; complete resources; working relative references; preserved licenses/provenance; no secret material; no unreviewed hooks; discovery in Codex; and no unintended application, hosted or global configuration changes. Use safe routing checks such as an RLS migration, a duplicate callback, an accessible filter panel and a proposed production backfill. The first three should select relevant guidance; the last must retain its existing owner approval boundary without starting a provider.
